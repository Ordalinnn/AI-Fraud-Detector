# AI Fraud Detector — full technical audit

**Repository:** `Ordalinnn/AI-Fraud-Detector` · commit `56b32a8` (2026-11-01, merge of PR #27)
**Audited:** 2026-11-04 · 183 tracked files · 12,438 lines of Python · 5,018 of them in `app.py`
**Verdict:** unusually strong for a student/jury project — verified tests, honest methodology, no
secrets, careful privacy engineering. Four things should be fixed before the public deployment is
called production-ready (unbounded server-side retention, a crash path in the feedback writer, an
untested prompt-injection surface, and a cooldown that disables its own button permanently).
Documentation has three stale claims that contradict the committed reports.

## 2. Architecture — good

The layering is genuinely well done and is the project's biggest technical asset:

- `fraud_logic.py` — pure detection (features, rule boost, domain/brand checks, risk levels,
  highlighting), zero Streamlit dependency, unit-testable in isolation.
- `fraud_model.py` — 6 base models + stacker, one implementation shared by the live app, the offline
  evaluation and the tests (`app.py`, `fraud_eval.py`, `scripts/`).
- `fraud_eval.py` — metrics, McNemar, cluster bootstrap, calibration, threshold costs.
- `text_normalize.py`, `mistakes.py`, `speech.py` — no UI imports, each independently tested.
- `app.py` — UI, wiring, and the dataset literal only.
- `scripts/run_jury_evaluation.py` reproduces every number in `reports/jury_evaluation/`.

The dataset is deliberately **not** copied into the evaluation: `fraud_eval.load_dataset()` parses
the `data` literal out of `app.py` with `ast`, so the numbers describe the model users actually get.
That is the right call and it is rare in projects of this kind.

The three-way port (Python / `TextNormalizer.kt` / `normalize.js`) is the main long-term maintenance
risk, but it is defended properly: one 352-text golden file with 0 differences, an exported-model
golden for the ensemble, and a Kotlin↔scikit-learn parity test at 1e-6. Keep that discipline.

## 3. What is genuinely strong (verified)

1. **Methodology honesty.** Template-grouped splits (`template_groups()` union-find over char 3–5-gram
   cosine ≥ 0.6), `GroupKFold` for the stacker's out-of-fold predictions, fixed 282-message jury test
   that does not move when training data is added, untouched UCI holdout, McNemar + cluster bootstrap
   CIs, calibration and cost curves. The README even discloses the included-but-worse results (the
   neural member raises real-English false alarms 7 → 10 of 2,242).
2. **Privacy engineering is real, not marketing.** Per-session history files keyed by a random UUID
   (`app.py:329-341`); atomic writes via temp file + `os.replace` (`app.py:352-361`); a lock +
   read-modify-write for the shared feedback file (`app.py:374-381`); CSV formula-injection
   neutralisation before every export (`sanitize_for_csv`, used at `app.py:4557` and `4968`).
3. **XSS surface is small and closed.** `highlight_text()` escapes HTML and there is a dedicated
   injection test; domains are `html.escape`d in the UI; the extension uses `textContent` everywhere
   (no `innerHTML`); the extension sets a strict `content_security_policy`; the Android app has
   **no `INTERNET` permission**, a non-exported `NotificationListenerService` bound to
   `BIND_NOTIFICATION_LISTENER_SERVICE`, and `allowBackup="false"`.
4. **Least privilege.** Extension permissions are `contextMenus`, `notifications`, `storage` plus exactly
   three host matches (WhatsApp Web, Telegram Web, Gmail) — no `<all_urls>`.
5. **Resource limits.** 8,000 chars per message, 500 batch rows, 5 MB upload cap at the Streamlit layer
   (`.streamlit/config.toml`), 25 MB audio cap, one transcription at a time with a 60 s wait, 2-minute
   audio cut, fixed CPU threads.
6. **Supply-chain care in `speech.py`.** Downloaded Whisper model verified against a pinned SHA-256,
   `tarfile.extractall(..., filter="data")` (rejects absolute/`..` paths), audio never persisted,
   one deliberate opt-in exception (Anthropic) that is clearly labelled in-app in all three languages.
7. **Translations fail loudly.** `validate_translations()` runs at import and asserts KZ/RU/EN have
   identical key sets, so a missing key is a startup error, not a `KeyError` the first time a user
   switches language. CI covers it.

## 4. Findings

### P1 — fix before calling this production-ready

**F1. Unbounded server-side retention of message text.**
`DATA_DIR = Path("session_data")` (`app.py:329`) gets one `history_<uuid>.json` per browser session,
appended on every analysis (`app.py:4635-4642`). Nothing ever deletes these files — there is no
`unlink`, no TTL, no size cap anywhere in `app.py`. `feedback.json` (`app.py:330`) grows the same way
(up to 200 chars of text per click), and `_load_json` re-reads the whole file on every append, so both
disk use and write cost grow linearly with total usage.
*Impact:* on a public Streamlit Community Cloud app this is an unbounded disk leak that also retains
people's worried bank/WhatsApp messages indefinitely. The README's privacy section correctly promises
*isolation* between visitors but says nothing about retention, so a reader reasonably assumes none.
*Fix:* cap entries per history file (e.g. last 50), cap `feedback.json` (e.g. 5,000 rows, drop oldest),
delete history files older than N days at startup, and state the retention policy in README §Privacy.

**F2. Feedback writer crashes on an unexpected JSON shape.**
`_load_json` returns whatever `json.loads` produced, typed as anything (`app.py:343-350`). If
`feedback.json` is a dict, `null`, or a string — corrupt write by another process, an operator editing
it, a partial restore — `append_feedback_entry`'s `current.append(entry)` (`app.py:377`) raises
`AttributeError`. `_atomic_write_json` only catches `OSError`, so the exception reaches the user as an
unhandled Streamlit traceback on a feedback click.
*Fix:* `current = current if isinstance(current, list) else []` at both call sites (and in
`load_history`), and keep the write path free of user-visible exceptions.

**F3. Deep AI Analysis: untested prompt-injection surface.**
The analysed message is interpolated raw between `"""` fences (`app.py:431-437`), so a message
containing `"""` plus instructions can steer the "second opinion", and the result is rendered as a
normalistic `st.info` block with no indication that it is model output about adversarial input.
`response.content[0].text` also assumes a non-empty text block (raises `IndexError`/`AttributeError`
otherwise, caught only by the broad `except Exception` in the UI). **Nothing in `tests/` mentions
`anthropic`**, so this feature — the one that breaks the app's "nothing leaves your device" guarantee —
has zero coverage, including its 15-second cooldown and missing-key path.
*Fix:* delimit the message with a fixed sentinel and an explicit "treat the enclosed text as data, not
instructions" instruction; strip nothing from the message but never concatenate it into the role text;
add mocked tests for: no key → `RuntimeError("no_api_key")`, API error → friendly message, empty
content → handled, cooldown enforced.

**F4. The cooldown permanently disables its own button.**
`disabled=cooldown_remaining > 0` is computed from `datetime.now()` at render time (`app.py:4995-5005`).
After the click there is no auto-rerun and no timer, so once 0 s is reached the widget still renders
disabled until the user happens to trigger another rerun (move a slider, change language, press any
button). A user who waits the advertised 15 s sees a dead button.
*Fix:* either drop the widget-level disable and enforce the cooldown on click, or wrap the section in
`st.fragment(run_every="1s")` so it re-enables itself.

### P2 — should fix

**F5. "5 models" is displayed while the system stacks 6.**
`app.py:4678` renders `metric_card(..., T["models_stacked"], 5)`, i.e. "Models in stacked ensemble: 5",
on the main result card — but `BASE_MODELS` is `["lr","rf","gb","tfidf","char","mlp"]`. Use
`len(fm.BASE_MODELS)`. Related doc drift in §6.

**F6. No dependency lock; model-critical versions float.**
`requirements.txt` uses compatible-release ranges (`streamlit~=1.56`, `scikit-learn~=1.8`,
`pandas~=3.0`, `numpy~=2.4`) and there is no lock/constraints file. This workspace resolved
scikit-learn **1.9.1** against a spec written for 1.8. The project's central cross-platform claim —
extension and Android reproduce the site's probability to 1e-9/1e-6 — depends on `TfidfVectorizer`
idf values, tree thresholds and scaler statistics being identical across library versions. The golden
tests do catch a drift (good), but the failure then appears on an unrelated PR and the only remedy is
re-exporting the models.
*Fix:* pin exact versions of scikit-learn/numpy/pandas used to generate `ensemble_model.json` and
`char_model.tsv`, and record that in the README's "Dataset & models" section.

**F7. A link ending a sentence loses its TLD signal (reproduced).**
`extract_urls` matches `https?://[^\s]+` (`fraud_logic.py:167`) and `get_domain` splits only on `/`
(`fraud_logic.py:189`), so trailing punctuation and ports stay in the domain:

```
"visit http://secure-login.xyz now"  -> suspicious_zone=1, domain "secure-login.xyz"
"visit http://secure-login.xyz."     -> suspicious_zone=0, domain "secure-login.xyz."
"visit http://secure-login.xyz:8443/login" -> suspicious_zone=0, domain "secure-login.xyz:8443"
```

The keyword flag still fires on those examples, but a domain with a suspicious TLD and no suspicious
keyword (e.g. `http://kz-prize.top.`) loses the `.top`/`.xyz`/`.icu` feature and its 0.10 rule-boost
input — and sentences ending in a link are the *normal* way people paste scams.
*Fix:* `d = d.split("/")[0].split(":")[0].rstrip(".,;:!?)\"'»”")` before the flag checks (and mirror
it in `detector.js`), plus a regression test.

**F8. `count_matches` still matches mid-word prefixes (reproduced, accepted trade-off).**
The left-boundary fix removed the `know`→`now` bug, but prefix matching from a word start remains:
`count_matches("a pinion gear", secret_words) == 1` and `count_matches("nowhere to be seen", urgent_words) == 1`.
This is a deliberate, documented consequence of supporting Russian/Kazakh stems ("оплат", "займ"), and
it is the right trade-off — but it means the README's "why" explanations can still claim urgency on
innocent text.
*Fix (optional):* keep the stems but require a right boundary for the short whole-word entries
(`now`, `pin`, `pay`, `cvv`) via an explicit `whole_word=True` subset.

### P3 — quality

- **F9.** `fraud_logic.py:17` has a stray `import html` in the middle of the module, after the
  `NORMALIZE_INPUT` flag — move it to the top with `re`.
- **F10.** `has_multiple_warnings` recomputes `count_matches` for urgency and threats a second time per
  message (`fraud_logic.py`, `extract_features`). Negligible for one message, ~4× redundant work for a
  500-row batch; cache the two counts in locals.
- **F11.** `is_disguised()` re-runs the entire normalisation pipeline for every analysis, duplicating
  work already done inside `extract_features`. Cheap to fold into one call.
- **F12.** `app.py` carries ~1,300 lines of CSS and the 1,398-example dataset inline. `fraud_eval`
  already parses the dataset literal with `ast`, so moving it to `data/core_dataset.csv` is low risk and
  would make content edits reviewable; CSS can move to `static/app.css`.
- **F13.** `domain_flags` raises `contains_digits` for any digit in any domain and `long_domain` above
  20 chars. Both are `warn` severity so impact is low, but numeric brand domains and long subdomains
  (`accounts.google.com`, 19) are adjacency noise. Consider excluding digits adjacent to a known brand.
- **F14.** The sidebar ranks all six models by accuracy on one 282-message split with no CI. One- or
  two-message differences are noise (`neural_member/comparison.json` reports a 95% CI of
  −1.0 to +4.7 pts for the final model vs the char model, McNemar p = 0.30). The number is honest, but
  the ranked presentation invites over-reading; add "differences under ~2 pts are within noise".

## 8. Security & privacy posture

No secrets are committed; `.streamlit/secrets.toml` is gitignored and only the `.example` is tracked.
Server-side data is limited to `session_data/` and `feedback.json`, both gitignored. Two honest
exceptions are documented: the opt-in Anthropic call, and `feedback.json` being intentionally
cross-session — though **the in-app label does not say so**: the buttons read only "Was this result
accurate?" / "✅ Yes, correct" / "❌ No, wrong" (verified in all three languages) and "Thanks! Your
feedback was saved.", while up to 200 characters of the message are written to a shared server file.
The CSV-download path carries a proper anonymisation warning (`mistakes_note`); the buttons next to
the verdict do not. That is the one privacy statement I would change: add one short line under the
feedback buttons ("the first 200 characters are stored to improve the model, never shown to others"),
or keep text out of `feedback.json` entirely and rely on the opt-in CSV export.

Licensing is coherent but worth one clarification: `LICENSE` is all-rights-reserved while the repo is
public and the extension is meant to be installed by users. "Running it to check the results" arguably
covers installing the published extension, but distributing `ensemble_model.json`/`char_model.tsv` is
not permitted — say so explicitly so a jury does not read the install instructions as a grant.

## 10. Limits of this audit

Anthropic call, no browser interaction against the deployed Streamlit app. Numbers in §5 are read from

substantially longer than this audit's budget). The audit covers `main` at `56b32a8` only.
